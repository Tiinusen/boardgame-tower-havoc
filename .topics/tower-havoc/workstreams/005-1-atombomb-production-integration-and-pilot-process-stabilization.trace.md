# Atombomb Production Integration And Pilot Process Stabilization

## Objective

Cartographer is the intended human-held design-continuity participant for this tranche. Materialize the Steward-accepted Atombomb production semantics and convert the validated Pilot lessons into a reusable Tower Havoc card-production process without rewriting historical provenance or bypassing Tooling qualification.

## Done Criteria

- the Atombomb Event lineage exposes the accepted production semantics: exactly one immediate Event that destroys all tower floors, all reinforcements, and all built Bells for every player;
- Bell destruction is reflected consistently wherever the Atombomb effect is projected or described, and rebuilding requires a new Bell plus the ordinary readiness/survival sequence;
- author the canonical 35-card Dud-free deck successor under the exact historical Dud-free deck Parent if current Tooling can now qualify that Parent; if it still cannot, preserve the exact blocker and do not reparent for convenience;
- only after a qualified 35-card deck successor exists, update deterministic deck-derived surfaces such as `data/cards.*`, component quantities, TTS deck material, generated documentation/manifests, and card-production planning to agree with 35 cards and seven Event faces;
- author a reusable successor to the current Tower Havoc Pilot-mediated card-generation process that preserves same-conversation human-authored image requests, minimal epistemic generation guidance, production-facing copy with no development meta, exact-source preservation, and final Steward acceptance boundaries;
- the reusable Pilot process must make the qualified return sequence explicit: human approval -> preserve exact result bytes -> `qualify-return` -> if qualified, follow `prepare-return` and Tooling-projected author/manufacture path -> qualify/orient the exact produced carrier -> expose exactly one human-visible Handoff Package plus routing text -> stop; if any gate blocks, expose the exact blocker and stop;
- the process must state that loose receipts are diagnostic evidence while the Handoff Package is the normal transport/recovery output, and that Pilot must not reconstruct carrier/pointer/package structure manually from precedent;
- future card-generation Handoffs reference the reusable process as Required Context and do not use historical test-Handoffs as semantic Parent merely to inherit procedure;
- do not promote the invalid historical Pilot return package as qualified provenance; either obtain a fresh qualified Pilot return for Atombomb art through the corrected process or preserve the current image only as explicitly noncanonical candidate/reference material;
- run all relevant Tower Havoc validators and Tiinex qualification paths; return exact blockers rather than bypassing them;
- produce one qualified Cartographer-to-Steward Handoff Package at the next meaningful stable frontier, unless this Handoff's explicit stable-major publication authority is used to commit/push the exact qualified source frontier first.

## Scope

Local Tower Havoc source/lineage/process/projection work required to reach the next stable Atombomb/card-production frontier. The work may include bounded delegation to Pilot, Keeper, or another already-qualified project Role when needed, but such delegation does not transfer Steward design acceptance.

## Stable Major / Remote Mutation Authority

The Cartographer holder may commit and push a stable Tower Havoc major to the already-configured project repository only when all of the following are true:

1. the committed bytes are the exact locally qualified source frontier produced under this Task/Handoff;
2. relevant project validators and required Tiinex qualification gates are clean, or any known non-blocking limitation is explicitly preserved in the durable lineage and does not make the claimed stable frontier false;
3. no unresolved gameplay/design choice is silently decided by the commit;
4. the push does not publish a release, change licensing/rights, deploy unrelated infrastructure, or mutate Tiinex Core/Business/VS Code repositories;
5. the commit/push is treated as repository transport of accepted Tower Havoc source, not as new semantic acceptance authority.

If those conditions are not satisfied, return a qualified Handoff Package to Steward instead of pushing an unstable or semantically incomplete major.

## Dependencies

- the Steward Atombomb fan-in/production Decision that parents this Task;
- current Atombomb Event and Bell rule lineage;
- current 34-card Dud-free deck Decision;
- current Tower Havoc Pilot-mediated card-generation process;
- current Cartographer, Pilot, Keeper, Player, and Steward Roles;
- qualified fan-out return findings summarized by the parent Steward Decision.

## Authority Boundary

Cartographer owns continuity analysis, local source materialization, validation, bounded decomposition, and the conditional stable-major repository transport above. Steward retains game-design acceptance, rights/licensing/publication policy, and acceptance of any new gameplay effect beyond the explicit Atombomb/Bell disposition already made.
